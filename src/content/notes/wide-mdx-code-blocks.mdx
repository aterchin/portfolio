This sits with the [portfolio design system](/notes/portfolio-design-system) notes: how the site is put together, written while it is still in flux. I wanted a few long code samples to breathe. Not every fence — just the ones that earn it. Josh Comeau does this on [his Anchor Positioning post](https://www.joshwcomeau.com/css/anchor-positioning/): the paragraphs stay narrow, and one demo is allowed to run wider, toward the table of contents.

The authoring API is one extra word on the fence:

````markdown
```bash wide
# this block may overflow the prose column
```
````

No flag, it stays with the paragraphs.

## Previous Layout

Notes and work posts were already two columns on a wide screen: article on the left, sticky ToC on the right. The readable text was not that left column. It was a max-width box *inside* it. Everything MDX rendered — including code — was stuck in that box.

Comeau’s article *is* the grid. Paragraphs occupy one column. The demo occupies that column plus a spare one he left empty on purpose. I never had a spare column. The ToC was already sitting in that space.

A child cannot be wider than its parent. If the parent has `max-width`, the code block has to break out, or the parent has to stop being the thing that sets the width.

## Modifications

First pass: turn the prose wrapper into a grid and let wide blocks span into whatever space was left in the article column. The inspector showed a grid. The page looked the same, even at a huge viewport.

Making the window wider does not help if the *page* has a max width. With the ToC on screen, the article column is already about as wide as the text. There was nothing left to span into.

Second pass: put the ToC on the same grid as the paragraphs and let a wide block cover both columns. That finally looked like Comeau. It also broke sticky — with or without the `wide` flag.

### Sticky ToC

`position: sticky` only works while its parent is still on screen, and that parent has to be as tall as the article.

The old layout had two grid items in one row: the article and the sidebar. The sidebar stretched to match the article. Sticky had a long runway.

The new grid made every paragraph and heading its own row. The sidebar was told to span “from the first row to the last,” but in CSS Grid that last line means the last *named* row, not “the bottom of the note.” The sidebar shrank to about the header. The ToC stuck for a moment, then its short parent scrolled away.

The inspector will still say `sticky`. It will not tell you the sticky parent is only as tall as the title.

## Fixes

Put the two-item layout back so the sidebar is tall again. Wide is not a grid span. Paragraphs keep a max-width. A `.code-wide` block is just wider than its siblings, and it is allowed to overflow.

This block is set to wide:

```css wide
.prose > .code-wide {
  width: calc(100% + var(--code-wide-extra, 0px));
  max-width: none;
  position: relative;
  z-index: 1;
}
```

- `--code-wide-extra` is the gap plus the ToC column, and only when a ToC is showing
- `z-index` so the code block glides over the ToC as you scroll
- `.main` has `overflow: visible` so the extra width of the code block is not clipped

Work posts use the same idea with a slightly narrower text column.

The `wide` word on the fence is **meta** — the bit after the language. MDX already turned `<pre>` into `CodeBlock` and read the language from a class name. Meta is thrown away on the way from markdown to HTML unless you copy it forward first. A remark plugin does that (`data-wide` on the `<pre>`). `CodeBlock` adds the `code-wide` class.

## Additional considerations

### Remark

Remark is a pipeline for markdown as a tree. A plugin walks that tree before anything becomes HTML or React. Rehype is the same idea one step later, on HTML. MDX runs markdown through remark, then into JSX. You pass plugins into `compileMDX` — it is not a separate tool you run in the terminal.

I had gotten by with React overrides (`pre`, `h2`, `Aside`) and a homemade heading scraper. Fence meta is not a React problem. It is gone before React exists.

You reach for remark when the default parse drops information, or when you want the same transform on every page without wrapping every fence in JSX:

- Fence meta: `wide`, filenames, line highlights
- Tables and other GitHub-flavored markdown, if you are not getting them already
- Cleaning HTML inside markdown
- Heading ids in the tree (we still do those in `MdxHeading`)
- Reading time from the tree instead of regex on the raw file

If `<Wide>` around a fence is enough, you can skip remark. I wanted the fence to stay a fence.

### mdxRemoteOptions

Until this, notes and work only passed `{ parseFrontmatter: false }` into `compileMDX`. Frontmatter is already stripped in `lib/mdx.ts`. There were no remark plugins, so there was nothing to share.

The plugin has to run on every page that might contain a `wide` fence. Copy-pasting the options object is how work posts get forgotten. `mdxRemoteOptions` lives next to `getMDXComponents()`, and both slug pages import it. First time this project needed a compile-options object, not just a component map.

```ts
export const mdxRemoteOptions = {
  parseFrontmatter: false,
  mdxOptions: {
    remarkPlugins: [remarkFencedCodeMeta],
  },
};
```

- `getMDXComponents()` is the React map
- Options are the markdown pipeline
- Same import path so I do not have to remember which file gets which
