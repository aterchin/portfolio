## Context

Pharma client needed a public tool to help patients find physicians who prescribe a specific specialty neurological product. Search by location, results on a map, switch to a list. Data came from a CSV of names and addresses, re-imported every night.

Front-end was the easy part.

<Aside variant="info" title="Stack">
  React on the front end, Laravel API, MySQL, Google Maps + Geocoding APIs.
</Aside>

## What it does

- Search by zip, city/state, or free-form address (Google Places autocomplete)
- Results on a custom-styled map and in a synced list
- Click a marker — highlights the list item; click a list item — pans the map
- Both views read the same React state, no coordination layer

## The problem

Every night the client's system dropped a fresh CSV on the server. Instruction: truncate the physicians table and re-import from scratch.

I pushed back. A CRUD interface would keep data stable and auditable. Short of that: diff-based import, or a geocode cache table that never gets truncated. They wanted the nightly wipe anyway.

<Aside variant="error">
  Truncating every night meant the database had no memory between runs — and
  an expensive geocoding problem.
</Aside>

Google Geocoding charges per request. Re-import 800 physicians, you don't want 800 geocode calls every night.

- Most addresses haven't changed
- Some physicians share an office
- Some CSV rows look different but resolve to the same coordinates

The constraint wasn't mine. The solution had to work around it.

## The seeder

Split *physician* and *location* into two tables — one-to-many. Many physicians can share a location; geocode each location once.

For each CSV row:

- Hash address parts (street, city, state, postal) with MD5 for a stable location ID
- Hash name + address for the physician—*catches duplicates at the same address*
- If the location hash already exists, skip geocoding and attach the physician to that location

```php
// Location hash — street + city + state + postal
$l_arr = [$street, $city, $state, $postal];
$l_hex = md5(implode('|', $l_arr));

// Physician hash — name + address (catches duplicate physicians at same address)
$p_arr = [$name] + $l_arr;
$p_hex = md5(implode('|', $p_arr));

$location_id = DB::table('locations')
    ->whereRaw("HEX(`location_hash`) = ?", [$l_hex])
    ->value('id');
```

One more check before inserting a new location: does the geocoding API's formatted address already exist in the database? Catches typos and abbreviations that still resolve to the same real-world address.

```php
// Geocoding API returned a canonical address —
// check if we already have it before inserting a new location record.
$location_id = DB::table('locations')
    ->where('address', $address)
    ->value('id');
```

<Aside variant="success" title="Outcome">
  Most nightly reimports hit the location hash cache — geocoding only ran for genuinely new addresses.
</Aside>

Typical nightly run: fewer than 5% of records hit the geocoding API. The rest match an existing hash and pass through.

## What I'd do differently

Nightly truncation was inherited, not designed. Diff-based import would have made most of the seeder unnecessary.

Works well within the constraint. Didn't need to be one.
