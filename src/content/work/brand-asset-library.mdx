I created a headless WordPress media library.  React on the front-end connected with a REST API.

## Context

My long-time pharma aesthetics client again.  Six product brands. Lots of media — images, video, social posts, before-and-after shots, in-office materials. All over the place.

Two audiences:

- **Brand managers** — add content without calling a developer
- **Field teams and HCPs** — healthcare professionals find and download what they need, no training


## Why WordPress for the backend

The team already knew WordPress. Non-technical staff could add a resource, attach files, pick a brand and media type, and publish — no code.

Two taxonomies:

- **Brands** — six product lines
- **Media Types** — Banner, Before and After, Celebrity, Image, In-Office Material, Social Media, Video

## The front-end

React, React Router, React Bootstrap, Vite.

A `useResources` hook fetches from the WordPress REST API, applies filters, and keeps results in sync as you move between brands and media types.

Filtering:

- Pick a brand — narrows to one product line
- Toggle media types — refines within that brand
- Sort by most recent or most downloaded

No page reloads. The REST API is fast enough that it feels native even with bigger result sets.  I also found a [wordpress plugin](https://wordpress.org/plugins/wp-rest-cache/) which caches the responses to make it even speedier.

## The download

Each tile has a download button. One resource can have multiple files — image, PDF spec sheet, video version. Expected behavior: one click, one zip.

Client-side zipping from WordPress media URLs is fragile.

<Aside variant="warning" title="Why not zip in the browser?">
  Public media URLs open in a tab — that does not mean JavaScript can `fetch` them. CORS often blocks it.

  Even when it works, every file has to load into browser memory before the zip exists. Image + PDF + video on one resource adds up fast.

  Worse: files travel server -> browser to build the zip, then browser -> user to download it. The server already has them on disk.
</Aside>

I made a custom REST route in a WordPress plugin instead. Front-end sends the resource post ID. The plugin:

1. Retrieves all media attached to that post
2. Fetches each file from the filesystem
3. Assembles a `ZipArchive` in PHP
4. Streams the zip to the browser with the correct `Content-Type` and `Content-Disposition` headers
5. Increments a download count field in the post's meta

```php
$media_ids = get_post_meta($post_id, 'resource_files', true);

foreach ($media_ids as $media_id) {
    $file_path = get_attached_file($media_id);
    $zip->addFile($file_path, basename($file_path));
}
```

Server-side streaming = normal file download. One request, one response.

## What I'd do differently

Download count increments in the same request as the zip. 
Failed or interrupted downloads still bump the count.

Better: a separate lightweight endpoint the front-end hits only after the download finishes. Fine for rough internal usage tracking. Not fine if you need accurate analytics.

That being said, we did add Google Analytics to track downloads as well as the modal popup which triggers a preview of the video or image resource which was fine with the client.
